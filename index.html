DevLog: Dynamic Underwater Rendering in Unity 6 URP – Overcoming Shader Stripping

After sorting out the underlying network logic for multi-adapter broadcasting and blocking out the foundational island terrain, our core focus over the past few days shifted to a critical visual pain point: the Dynamic Underwater Rendering System.

Seamless visual transitions between the surface and underwater are key to enhancing immersion in a marine-themed game. Under the Universal Render Pipeline (URP) and Render Graph API architecture in Unity 6, achieving the ideal visual effect required a hardcore battle, ranging from “mathematical formula synchronization” to “graphics pipeline debugging”.

🌊 Core Mechanism 1: Dynamic Wave Sync via IWaterSurface

The first challenge in underwater rendering is boundary detection. If we simply judge whether the camera is underwater based on its absolute height (Y-axis), we get extremely immersion-breaking “instant screen cuts” when the water surface fluctuates due to waves.

To achieve perfect physical and visual consistency, we introduced the IWaterSurface interface:

  • Real-time Wave Height Sampling: Through this interface, the UnderwaterVisuals controller can obtain the exact dynamic wave height at the camera’s current horizontal coordinates (X, Z) in real-time.
  • Logic Gate Calculation: The underwater state machine is precisely triggered only when the camera’s height falls below the dynamic wave height at its exact position. This ensures that whether the sea is calm or stormy, the moment the camera enters or exits the water, the visual alignment is flawless.

🎨 Core Mechanism 2: Depth-Based Post-processing Fog

Once underwater, the entire screen needs to convey the oppressive yet beautiful atmosphere of the deep sea. We built this effect using custom HLSL scripts and URP’s Post-processing Volumes:

  1. Screen-Space Underwater Fog: We use the camera’s Depth Texture to calculate the linear depth of every pixel on the screen, which drives the density of the underwater fog. The further an object is from the camera, the deeper the blue tint and the lower the visibility.
  2. Seamless Post-processing Transition: When the camera is completely submerged, a dedicated underwater Profile is dynamically enabled. This integrates tweaked global fog, Color Grading, and custom Bloom effects to create the gorgeous, scattered light ripples of sunlight piercing through the water’s surface.

🚨 The Final Boss: Missing Effects and Shader Variant Stripping

When testing in the Unity Editor, the entire underwater effect was absolutely perfect, with light and shadows rippling beautifully. However, when we built the project and sent it out for cross-platform multiplayer testing, something bizarre happened: Once the game was built, the underwater effects went completely blind. The entire seabed was a stark white, with no fog or color shifts whatsoever.

Since there are no error logs in a built game for this kind of issue, we had to trace back step-by-step through the graphics pipeline’s build process. We eventually pinpointed an extremely sneaky underlying optimization mechanism: Shader Variant Stripping.

Root Cause Analysis:
To optimize build size and reduce runtime GPU memory usage, Unity 6 employs highly aggressive shader optimization during the build process. Because our underwater shader variants and specific post-processing Keywords are dynamically enabled via scripts at runtime based on dynamic wave data (IWaterSurface), Unity mistakenly assumed during the static scene compilation that these custom fog effects and rendering variants “were never directly referenced by any material in the scene.” Thus, it “smartly” stripped and discarded these variants entirely!

The Solution:
Once the root cause was identified, prescribing the fix was straightforward. To stop Unity’s overzealous optimization, we implemented a two-step defense:

  1. Forced Keyword Retention: In the URP Shader settings, we elevated the crucial underwater rendering feature keywords to “globally forced,” explicitly telling the compiler that these variants cannot be stripped.
  2. Always Included List: We manually added the core post-processing and underwater HLSL shaders into the Graphics Settings -> Always Included Shaders list. This ensures they are fully compiled and included during multi-platform builds.

🚀 Summary and Next Steps

This debugging experience profoundly taught me that “Editor performance does not equal Build performance.” Battling the compiler’s optimization strategies deep within the graphics pipeline was painful, but seeing the built version perfectly render the deep, dynamic underwater visuals brought an unparalleled sense of accomplishment.

At this point, our project boasts a robust network lobby, interference-resistant directed broadcasting, complete level terrain, and a high-performance underwater visual system. In the next DevLog, we will focus on the multiplayer synchronization of our core gameplay mechanics (Sailing & Interacting).

The ocean stage is perfectly set; it’s time to let our ships truly sail!

DevLog: Building Islands and Seabeds from Scratch – Prototyping Environments with Free Prefabs

If the past few weeks of wrestling with UDP network broadcasts and UI state machines were about laying the foundation, the work over these past few days has been about actually “building the house” on top of it.

With the network multiplayer and the pause menu (featuring the network diagnostic panel) running smoothly, our project has finally crossed the deep waters of underlying technology and officially entered the level blockout/prototyping phase. Today’s log is about the birth of the basic foundation of our game world—the islands and the seabed.

🏝️ Charting the Course: Starting and Destination Islands

Our core gameplay loop unfolds across different islands. To quickly validate the gameplay, my primary goal for this phase was to construct two key landmarks: the Starting Island and the Destination Island.

As a student team, modeling everything from scratch is obviously unrealistic and would severely slow down our progress. Therefore, I adopted a common rapid prototyping strategy used in the industry: clever use of free prefabs.

By hunting down high-quality free environment assets (rocks, vegetation, terrain materials, etc.) from the Unity Asset Store and open-source communities, I was able to snap together the outlines of two distinctly styled islands like Lego blocks.

  • Starting Island: Primarily serves as the spawn point, tutorial area, and initial resource gathering zone. The terrain is relatively flat, visually providing the player with a sense of safety.
  • Destination Island: Acting as the milestone for the voyage, its terrain design is more complex. Viewed from the open ocean, it needs strong visual guidance (such as taller peaks or a unique silhouette).

🌊 Bridging the Gap: Sculpting the Seabed

The two islands don’t exist in isolation; they are connected by a vast ocean. To ensure the voyage isn’t monotonous, I also built the Seabed topography connecting the two landmasses.

Using Unity’s Terrain tools combined with prefabs of underwater rocks and coral, I sculpted an undulating underwater landscape.

Here, a previous technical achievement really shined:
The URP dynamic underwater visual effects (global fog and depth testing) that I spent so much effort on earlier had their highlight moment here! When the scene was assembled and the camera dove underwater, the rough edges of the model seams were perfectly softened by the underwater fog. Sunlight refracted through the water surface onto the uneven seabed, instantly maximizing the scene’s immersion. At that moment, I truly felt like the world had come alive.

🚀 Phase Summary and Next Steps

Using free prefabs for white-boxing/prototyping has immensely optimized my workflow. It allowed me to focus my precious energy on the “Level Flow” and a sense of spatial scale, rather than getting bogged down tweaking the normal map of a single rock.

Currently, the basic scene structure of the game is established. The two islands and the seabed not only provide physical space for the upcoming sailing gameplay but also serve as an excellent testing playground for our cross-platform LAN multiplayer.

In the next Sprint, we will drop the finalized Player Controller into this scene to conduct real movement and multiplayer interaction tests. The stage for our voyage is set—it’s time to set sail!

AddingPauseMenu

Today we had a team sync to align our milestones and distribute upcoming tasks. My primary objective for this sprint was to implement a functional Pause Menu that doubles as a network diagnostic tool for our multi-platform testing.

I successfully built the UI overlay featuring a semi-transparent gray filter and real-time network statistics, including Local IP, Host IP, and a Ping indicator. To ensure the menu doesn’t interfere with our initial connection screen, I implemented a logic gate using NetworkManager.Singleton.IsListening. This ensures the Tab key only activates the menu once a network session is actually live, keeping the starting interface clean.

The main technical hurdle was resolving the “input war” between the UI and my existing PlayerMove.cs. I handled this by utilizing a static IsPaused flag to act as a master switch. Now, when the menu is active, it completely intercepts player movement and rotation logic. This fixed a critical bug where mouse clicks were being “stolen” by the player controller, which previously prevented buttons from responding. The system is now robust, allowing for seamless transitions between gameplay and menu navigation. All changes have been pushed to the feature branch for further integration.

CreateGithubPage & Core Multiplayer Architecture

Devlog: Laying the Foundation for LAN Multiplayer Collaboration

Today’s core objective was to transition our project from a standalone single-player demo into a robust multiplayer collaborative engineering effort. We refactored all core scripts and established a standardized distributed version control workflow.

1. Core Network Architecture (NGO Implementation)

We adopted Unity’s Netcode for GameObjects (NGO) framework and deeply customized it for the flexibility of Local Area Network (LAN) multiplayer:

  • Dynamic IP Connection: Refactored NetworkUI.cs. By introducing the UnityTransport component, we enabled dynamic modification of ConnectionData at runtime. Clients can now directly input the Host’s LAN IP via the UI to connect, completely eliminating the pain point of hardcoding localhost for LAN testing.
  • Client-Side Component Isolation: Wrote PlayerSetup.cs. Using the OnNetworkSpawn hook, we dynamically toggle the Camera and AudioListener based on the IsOwner status. This ensures that in a multiplayer environment, each player only sees the world through their own perspective, avoiding Unity rendering and audio conflicts.

2. Physics & Visuals Synergy (Buoyancy & Waves)

To handle ocean wave synchronization, we opted for a low-bandwidth, high-performance deterministic algorithm:

  • Deterministic Waves: WaveManager.cs uses the global absolute time Time.time to drive the sine wave formula. Because this mathematical formula is identical across all connected Clients, we achieve perfect visual alignment purely through local calculations, without needing to sync thousands of vertex coordinates over the network.
  • Server-Authoritative Buoyancy: Floater.cs strictly adheres to server-authoritative logic. Physics forces (AddForceAtPosition) are calculated ONLY on the Server/Host. The resulting transform data is then synced across the network via NetworkTransform, ensuring the ship’s bobbing motion is consistent and stutter-free for all players.

3. Environment & Spawn Logic

To improve the testing experience, we added a “Coast” module to the scene:

  • Static Anchor Point: Created a PlayerSpawnPoint and adjusted the default spawn coordinates of the player prefab. This allows joining players to safely land on solid ground to observe the waves, rather than spawning directly into the deep ocean.

4. Engineering & Version Control (Git / GitHub)

To kick off team collaboration, we officially set up the remote repository with “industry-standard” safeguards today:

  • Git LFS Configuration: Pre-configured Git Large File Storage to track large assets like *.fbx and *.png. This prevents our .git repository from bloating when we introduce high-poly ship models later.
  • Standardized .gitignore: Created a Unity-specific .gitignore (with English comments) to strictly filter out local cache directories like Library and Temp.
  • Code Standardization: Upgraded all core scripts (Floater, NetworkUI, PlayerMove, PlayerSetup, WaterMeshGenerator, WaveManager) with professional English comments and added File Headers to clarify each script’s role within our distributed architecture.

5. Next Steps (Roadmap)

  • Optimize player physics/attachment logic on the ship (addressing relative transform synchronization).
  • Introduce the first-pass 3D ship model to replace the current placeholder Cubes.
  • Conduct the first cross-platform (Mac/Windows) multiplayer stress test once the team pulls the code.

Current Status: 🏗️ Base architecture pushed to GitHub. Ready for team collaboration.

Using ParrelSync to Simulate Multiple Players & FPS Setup

Project Blog DH2650 - Setting up the Multiplayer Foundation

1. Decide Game Topic & Technical Stack

For our project, we are building a multiplayer experience where players interact on a moving ship affected by ocean waves. To handle the networking architecture, we decided to use Unity’s Netcode for GameObjects (NGO). For local testing, we are utilizing ParrelSync, which is an absolute lifesaver. It allows us to open a clone of the project editor to test Host/Client interactions seamlessly without needing to build the game every time.

2. Establishing the NetworkManager & Syncing the Environment

The core of the NGO setup is the NetworkManager combined with Unity Transport. Our first technical milestone was getting the ocean physics to sync.
By registering our Ship as a Network Prefab and attaching both a NetworkObject and NetworkTransform, we ensured that the wave-driven physics calculated on the Host are perfectly replicated across all Client instances. It’s a highly satisfying visual validation of state consistency in our distributed environment.

3. First-Person Player Setup & “Owner-Driven” Cameras

Spawning players into a multiplayer scene introduces a classic problem: if every player prefab has an active camera and AudioListener, the client screens will conflict and glitch out.
To solve this, we implemented an ownership-check script (PlayerSetup.cs). By utilizing OnNetworkSpawn() and checking IsOwner, we ensured strict isolation:

  • Local Players: Activate their own camera, lock the cursor, and handle their own input.
  • Remote Players: Keep their cameras and listeners disabled to prevent them from hijacking the local screen.

4. Overcoming the “Server Authority” Trap

When implementing the WASD and mouse-look movement (PlayerMove.cs with a CharacterController), we hit a wall: the Host could move perfectly, but the Client was stuck twitching in place.
This was a harsh but necessary lesson in Server Authority. The NetworkTransform component defaults to Server authority. As a result, the Client’s local inputs were constantly being overridden and rolled back by the Server’s absolute state. By switching the Authority Mode to Owner, we successfully decentralized the movement control, granting clients the authority to drive their own positional state while broadcasting it to the network.

5. Optimizing the ParrelSync Dual-Window Workflow

Testing a First-Person game with locked cursors in two ParrelSync windows can lead to input chaos (e.g., moving the mouse in one window rotates the camera in the other).
We optimized our debugging workflow by implementing a window focus check:
if (!Application.isFocused || Cursor.lockState != CursorLockMode.Locked) return;
Combined with an Escape-key toggle to unlock the mouse, the scripts now simply ignore input if the specific game window loses focus. This makes dual-window testing perfectly smooth and isolated.

Next Steps: With the multiplayer foundation and FPS controllers fully synced, the next challenge is physics-based: ensuring the players can stand firmly on the pitching and rolling deck of the ship without sliding into the ocean.
